# 单人开发流程

把一个需求推进到用户要求的交付状态。默认连续完成已授权工作，按改动规模裁剪流程；每个需求优先复用一份功能记录。遵守当前项目规则与用户已确认决定。

## 先确定本次范围和入口

- 读取适用的项目指令、README、当前需求和相关代码；确认分支、代码基线、已有工作区改动和实际依赖版本。
- 优先沿用现有需求、任务和测试记录；已有材料足够时直接引用，不创建一套重复文档，也不重写历史基线。
- 继续已有需求时先定位其记录、剩余验收项和未交付改动；有多个无法区分的入口再澄清。
- 用户只要求梳理、方案、评审或文档时，完成所要求阶段。用户要求实现时，进入实现并验证。
- 若确认为“宝宝计划”项目，按需读 [项目适配](references/baby-plan.md)。其他项目不加载该文件。
- 仓库要求按已安装框架版本读取文档时，写代码前落实；不将旧版经验当作当前接口依据。

## 按影响选择流程

| 模式 | 判定 | 记录与检查 |
| --- | --- | --- |
| 快速 | 局部文案、样式等可逆改动，不改变业务规则、权限、数据或契约 | 在现有任务或提交说明记录目标、变化及适当验证；通常不新建功能单 |
| 标准 | 新功能或可观察行为变化，边界清楚 | 复用现有规格，或按 [功能单母版](assets/feature.md) 保留一份记录 |
| 扩展 | 涉及授权、数据隔离、收费、迁移、并发写入、外部副作用或产品内 LLM 行为 | 标准流程加相关风险检查；按需读 [扩展检查](references/extended-changes.md) 的相关小节 |

根据实际影响判定，不能仅因改动文件少就走快速流程。发现影响扩大时更新范围与检查计划，无需为了切换模式单独请求批准。

## 1. 把需求写成可验证行为

在开始相关实现前，明确：

- 谁在什么条件下，做什么操作，获得什么结果。
- 本次范围、排除项及需要保留的既有行为。
- 正常路径和适用的权限、状态、边界、错误与恢复。
- 用 AC-01 等少量编号记录可观察结果，关联检查方式。

用户已给出明确需求，或现有基线已有决定时直接采用。关键歧义影响权限、金额、数据、业务规则或不可逆行为时，只澄清受影响问题，继续独立工作。非关键且可撤销的实现选择采用项目惯例并记录必要假设。不逐阶段要求用户确认。

## 2. 确定最小必要方案

- 检查现有模块、组件、接口与测试，确定需要改动的路径和依赖。
- 简述实现方法、为何适合现状，以及必要的兼容、失败恢复和迁移方式。
- 契约和数据结构引用已有权威定义，避免在多份文档重复维护字段。
- 拆成可独立检查的动作，注明与 AC 的对应关系；复杂度不足时不额外建立任务树或 ADR。
- 沿用已确认架构。只有实际问题需要时才增加依赖、服务或基础设施。
- 项目说明、AI 约定、运维材料缺失且影响本次任务时，补足必要内容；不为套流程自动生成三份常驻文档。

## 3. 实现并随改动验证

- 保留用户和其他任务的既有修改，只实现当前范围内必要行为。
- 针对业务规则选择或补充有意义的验证。需要回归保护的行为先明确如何暴露错误；用户要求测试先行时遵循该要求。
- 预期结果来自已确认 AC、契约或独立业务样本，不能仅复用新实现计算唯一预期。
- 小型可逆改动采用与影响相称的检查，不为每一行实现增加镜像测试。
- 发现新业务选择或方案冲突，记录证据和影响；在现有授权内完成独立部分，不顺带扩展需求。

## 4. 验证到适当程度

- 从仓库配置、开发指南和当前测试入口取得真实命令，不猜测脚本名或套用其他项目命令。
- 先运行相关检查，再完成项目要求的必要检查；通过后不无依据反复全量重跑。
- 用户界面变化检查实际交互和适用状态；使用项目已有页面验证方式。构建成功只能证明构建结果。
- 持久化、权限、并发或外部服务变化，按适用风险检查可信边界、最终数据状态和副作用。
- 记录实际版本、环境、命令或人工步骤、退出状态、结果和证据位置。首次失败保留；修复后做相关回归。
- 区分模拟与真实接入、用例设计与实际执行、技术验证与用户验收。未执行或受阻不能记为通过。
- 对已有失败标注基线与本次改动的关系；不通过放宽验收或删除断言迎合错误实现。
- 环境或外部条件受阻时，完成不依赖该条件的工作，并保留具体缺口。

## 5. 更新记录并交付

检查最终差异是否符合 AC、契约和当前范围，更新真正发生变化的任务、文档或运维入口。

交付说明应包含：

1. 实际行为变化与关键位置。
2. 已执行的验证、对应证据与适用范围。
3. 尚未完成、未验证或仍受阻的部分及影响。
4. 如果需要继续，明确下一项动作和所需条件。

适用验收项有有效证据、必要检查完成且所要求交付已落实，才标记该范围完成。开发完成、待真实接入、待发布、已发布待观察分别记录；不能把“已写代码”当成端到端完成，也不能虚构用户验收。

提交、推送、PR、部署和外部写入按照用户要求与既有授权执行。需求编码本身不推定这些动作已获授权；已获授权的必要动作持续完成，不重复询问。若本次包含发布，落实相关操作、目标环境核对与发布后检查。

## 续接与状态

优先把以下信息留在同一功能记录末尾：有效需求与代码版本、已完成和证据、未完成与原因、未交付改动的归属、下一步入口。默认不再创建另一份进度报告。

再次调用时从未完成部分继续，检查旧证据对当前版本是否仍有效；不重做已经完成且未受影响的步骤。
