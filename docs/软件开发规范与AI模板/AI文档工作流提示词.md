# AI 文档工作流提示词

这些提示词用于协助起草和检查，不能替代真实需求决定、运行结果和验收记录。先填入材料路径，再选择当前阶段的提示词；无需一次执行全部流程。

## 0. 每次任务附上的上下文

```text
项目：
当前目标：
需求 / 设计基线：
当前代码分支、commit 与已有工作区改动：
仓库规则与开发指南：
本次任务与允许修改范围：
可使用的环境与真实依赖：
用户已授权的动作与明确限制：
预期交付物与完成判断：
```

## 1. 从原始材料编写需求

```text
请阅读提供的访谈、讨论、工单和现有文档，使用 01-产品需求PRD.md 和
02-功能规格SRS.md 编写本次功能文档。

先整理：已确认事实、待验证假设、相互冲突信息、关键待定问题。
每条业务需求标记来源，使用稳定的 OBJ / US / FR / NFR / AC 编号。
写明范围、排除项、角色、状态、权限、异常与恢复。
验收使用具体输入、初始状态、触发和可观察结果。
数字阈值、日期、预算和角色规则必须有材料依据；没有依据则保留 TBD，
说明责任角色与受影响范围，不要替我决定业务。
此任务交付文档；不将草稿标为已确认，不实现代码。
最后列出：可以进入设计的部分，以及仍会阻塞相关开发的问题。
```

## 2. 编写技术方案与接口契约

```text
依据已经确认的 SRS，结合当前仓库和实际依赖版本，填写 03 和适用的 04。
先核对现有实现、可复用模块、真实技术约束与对应版本官方文档。
将观察到的事实、技术假设、建议方案分开。
比较最小可行方案与有实际差异的备选方案，说明取舍。
定义模块责任、授权位置、状态转换、事务、一致性、并发与重试。
涉及接口时明确参数、缺省、错误、权限、幂等、兼容和数据生命周期。
涉及迁移时写清新旧版本如何共存、如何核对、如何恢复。
每个设计项关联 FR / NFR / AC，不扩展产品范围。
最后给出需要验证的技术假设与验证方式；未经运行的设计不要描述为已验证。
```

## 3. 拆分可执行任务

```text
根据 SRS、技术方案和接口契约，使用 06-AI执行任务单.md 组织任务。
按可独立验证的行为拆分，任务注明依赖，按可执行顺序排列。
每个任务写明需求与 AC、必读文件、允许修改位置、预期交付物、
对应验证、恢复方式和完成判断。
任务大小以能够审查行为和证据为准，不按固定文件数量机械切分。
基础设施工作说明工程目标，不伪造产品需求。
识别关键待定问题，标记其阻塞范围，同时保留可以独立推进的任务。
当前只产生任务计划；所有未执行任务保持“待开始”。
```

## 4. 根据任务实施并验证

```text
执行指定 TASK，遵守当前有效仓库规则和用户已经授权的范围。
先确认代码与工作区状态，读取任务关联的规格、设计、契约及已有测试。
保护其他任务和用户改动，完成与目标相称的最小实现。
对陌生 API 查实际版本文档；不要编造接口或创建不必要的依赖。
测试从 AC 推导，采用能发现实际错误的断言。
执行与改动风险相称的检查，保存命令、版本、环境、退出状态和证据。
环境受阻时明确哪些未执行，继续完成不依赖阻碍的工作。
最后同步任务与必要文档，说明行为变化、实际验证、限制和下一步。
不要将自己生成的预期结果、示例日志或模型自检当成实际运行证据。
```

## 5. 设计测试计划和用例

```text
以已确认的 SRS 和 AC 为主要预期依据，使用 07 和 08 设计测试。
技术方案用于识别集成和失效风险，不能自行改变业务预期。
覆盖适用的正常、权限、跨数据范围、状态、输入边界、重复、并发、
时间、依赖失败和恢复情形；不适用时说明原因。
每条用例写清前提、具体数据、步骤、响应、持久化及副作用断言、
数据准备与清理、适合的层次、预期依据。
列出真实依赖与替身的验证边界，并给出进入和退出条件。
检查断言是否能识别典型错误，避免只验证被测代码的内部写法。
本次只编写计划与用例，所有结果保持“未执行”。
同时更新 10，区分覆盖计划与实际验证。
```

## 6. 审查文档、实现与测试的一致性

```text
检查指定版本的 PRD、SRS、设计、契约、任务、代码与测试是否一致。
按需求正向追踪到实现与验证，再从代码和测试反向检查来源。
重点查找：需求遗漏、无来源扩展、字段和状态冲突、权限口径不同、
并发与幂等歧义、没有断言的测试、失效证据、未执行却标记通过。
测试预期应追溯到 AC，不能因为代码输出不同就自动接受其行为。
输出发现表：严重程度、精确位置、证据、影响、建议修复与受影响编号。
实际未读取或未运行的部分明确列出；不能仅凭文件名称判断已覆盖。
如果没有发现问题，仍说明审查版本、范围和限制。
```

## 7. 整理验收与交接材料

```text
仅依据实际代码、运行记录和用户确认，填写 09，并同步 10。
区分用例设计、测试执行、测试通过、技术交付建议和业务验收。
按唯一用例汇总通过、失败、受阻、未执行、不适用，核对总数和分母。
证据记录实际代码、配置、环境和产物，旧证据说明当前适用性。
列出未验证范围、残留缺陷、影响、规避方式及下一步负责人。
只有真实存在确认记录时才填写验收人和验收通过。
若准备部署，再按 14 形成可审查的发布与恢复步骤，遵循现有授权，
不因模板自行增加新的批准流程。
最后给出接手者可直接继续的任务入口和未交付文件归属。
```

## 8. 已有项目补建文档

```text
从仓库、配置、测试、接口和已有操作记录补建项目文档。
分别保存“代码当前表现”“已有材料确认的目标”“未知或冲突”。
现有代码中的 Bug、临时绕过和缺失校验不能自动变成业务需求。
每项现状给出版本和文件依据；运行事实只来自实际执行。
先形成系统与功能索引，再按风险补齐 SRS、契约、测试计划和运维说明。
用 TBD 记录无法从材料确认的业务选择，避免伪造历史决定或批准。
输出优先补文档清单，优先处理会影响当前开发与交付的缺口。
```

涉及产品内 LLM 能力时，另使用 17 补充模型、提示词、数据集、工具权限、
评判标准、重复评测、成本与回退；不能拿通用代码测试替代模型行为评估。
