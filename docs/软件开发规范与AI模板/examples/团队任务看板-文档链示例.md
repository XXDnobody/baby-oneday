# 完整示例：团队任务看板的“完成任务”

这是虚构项目的填写示例，用来演示文档链如何连接。以下业务选择仅属于示例，不代表“宝宝计划”的需求、代码实现、实际测试或人员批准。所有运行状态均保持“未执行”。

## 1. 产品需求片段

| 项目 | 填写示例 |
| --- | --- |
| 用户问题 | 小团队需要知道一项任务是否完成，避免每天反复口头核对。 |
| OBJ-001 | 让工作区成员能完成任务，并让其他成员刷新后看到相同状态。 |
| 业务指标 | 首轮试用采集“每日用于核对状态的时间”，当前基线未知；本示例不编造提升比例。 |
| US-001 | 作为有效工作区成员，我希望把任务标记为完成，以便团队了解进度。 |
| 本期范围 | 单项任务的完成接口、数据一致性与权限。 |
| 排除范围 | 撤销完成、批量完成、通知、离线同步和前端界面设计。 |

后续只有确认这些范围与规则，才应在真实项目中形成开发基线。

## 2. 功能规格片段

### 术语

- 有效成员：调用时仍在目标工作区中且成员状态为 active 的已认证用户。
- 任务状态：OPEN 或 DONE。
- version：任务的正整数版本；每次真实状态变化加 1。
- 完成审计：记录一次真实的 OPEN → DONE 转换，包含任务、执行人、转换前后版本与时间。

### FR-001：完成行为

有效工作区成员可以将所属工作区的任务从 OPEN 改为 DONE。首次完成时 version 加 1，并恰好写入一条完成审计。当前已经为 DONE 且请求版本仍匹配时，返回成功，版本和审计数量均不变。

验收：AC-001、AC-005。

### FR-002：身份与数据范围

未认证请求返回 401。已认证但不属于目标工作区、成员无效、任务不属于该工作区或任务不存在时，统一返回 404；不能暴露其他工作区的任务信息。所有拒绝请求不修改任务或审计数据。

验收：AC-002、AC-003。真实项目还应将“无效成员”“任务不存在”等分支补充为适用用例；本示例的 8 条用例仅展示主链，不宣称覆盖全部输入分区。

### FR-003：并发与条件请求

- 请求必须携带单个数字版本的 If-Match，例如 `"4"`；缺少时返回 428，格式不符合该约定时返回 400。
- 先完成身份与对象范围检查，再校验条件头，避免借版本错误探测其他工作区对象。
- 请求版本与当前版本不符时返回 412；**先检查版本，再判断是否已完成**。
- 状态修改、版本增加和审计写入必须共同成功；失败时不能部分提交。
- 两个携带相同有效旧版本的并发完成请求，恰好一个返回 200，另一个返回 412；只产生一次版本增长和一次完成审计。

验收：AC-004、AC-006、AC-007、AC-008。

**重复请求的具体含义：** 首次以版本 4 完成后，服务器变为 DONE / version 5；再次携带版本 4 应返回 412。先读到当前版本 5，再携带版本 5 完成，返回 200 且不产生新审计。操作不会重复产生业务副作用，但旧请求的响应并不保证与首次相同。

## 3. 技术方案与契约片段

本示例假设使用支持事务、行锁和唯一约束的数据库，不指定真实框架或 SDK。

### DES-001：一致性实现

1. 验证调用者身份。
2. 在事务中确认有效成员关系，并以可靠的一致性方式保持该授权判断到写入；本示例采用锁定相关成员记录，成员撤销路径也遵守同一锁定顺序。
3. 按工作区和任务 ID 找到并锁定任务；对象不在可访问范围时返回 404。
4. 校验 If-Match；缺少、格式非法和版本不符分别处理。
5. 若已经 DONE，返回现有状态，不写新审计。
6. 若为 OPEN，更新状态与版本，并在同一事务写入审计。
7. 提交后返回成功；提交失败不报告完成。任务写入与审计共同回滚。

审计的“任务 ID + 目标版本 + 动作类型”建立唯一约束，作为一致性保护。真实实现仍需检查数据库隔离、锁顺序与死锁重试；不能仅因采用事务就认定全部并发问题已解决。

### API-001

| 项目 | 定义 |
| --- | --- |
| 方法 / 路径 | POST /workspaces/{workspaceId}/tasks/{taskId}/complete |
| 请求体 | 无 |
| 条件头 | If-Match：单个带双引号的正整数版本，如 `"4"`；不接受通配符或多值 |
| 认证 | 来自本项目可信认证机制，不从请求体接收用户身份 |
| 成功响应 | 200；字段 id、status、version |
| 错误 | 400 格式非法、401 未认证、404 无可访问对象、412 版本不符、428 缺少条件头 |
| 未预期的内部故障 | 返回项目统一内部错误，保留请求追踪信息，不暴露堆栈；客户端应重新查询结果后再决定操作 |
| 成功副作用 | 仅真实转换时更新任务与写入审计 |

### 数据不变量

- task.workspace_id 决定任务归属。
- task.status 与 task.version 只能按已定义规则一起变更。
- 相同任务、目标版本和完成动作最多一条审计。
- 无权限、格式或版本拒绝不能产生业务写入。
- 所有返回成功的真实转换均有匹配审计。

### TC-006 的详细定义

- 前提：独立测试空间、有效成员、任务 OPEN / v4、无该任务的完成审计。
- 准备：保证两个独立请求携带相同条件头；并发测试通过明确同步点交叠，不依赖随意延时。
- 步骤：同时触发请求，等待两者结束，收集各自响应，再独立查询任务和审计。
- 预期：响应状态集合 {200, 412}；最终 DONE / v5；完成审计为 1 条；审计执行人和版本与成功转换一致。
- 无效实现反例：两个请求都返回 200；版本变为 6；写入两条审计；任务完成但没有审计。
- 证据要求：实际构建版本、数据库版本、请求结果、最终状态、用例退出状态。
- 清理：删除本次测试专属空间及其数据；失败时也保留脱敏证据并清理残留。
- 执行状态：未执行；本示例未生成虚构命令、日志或截图。

后续应补充事务中断、审计失败、成员撤销竞争和历史版本重试等用例，以覆盖该方案的其他风险。
