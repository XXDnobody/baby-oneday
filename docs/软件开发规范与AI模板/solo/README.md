# 单人维护精简版

版本：1.1 · 编写与复核日期：2026-10-31 · 适用：一位维护者 + AI 辅助开发

原 18 份模板可作为字段资料库。对你目前的维护方式，建议固定为 **3 份仓库文档 + 每个有意义的功能 1 张功能单**。以下是基于维护成本作出的工程建议，不存在适用于所有一人公司的统一架构认证。

要让编码代理按这套方式处理新需求，见 [开发流程与 Skill 使用](开发流程与Skill使用.md)，可使用 `$solo-dev-workflow` 调用。

## 1. 只维护四类文件

| 文件类型 | 使用模板 | 保存内容 | 何时更新 |
| --- | --- | --- | --- |
| 项目说明 | [项目说明模板](01-项目说明.template.md) | 产品目标、技术结构、启动与检查命令、文档入口 | 环境、入口或目标变化时 |
| AI 协作约定 | [AI 协作模板](02-AI协作.template.md) | 必读位置、改动边界、验证与交接规则 | 工作方式变化时 |
| 功能单 | [功能单模板](03-功能单.template.md) | 本次行为、验收、必要方案、任务和实际验证 | 功能开发期间维护同一份 |
| 上线与运维 | [上线与运维模板](04-上线与运维.template.md) | 部署、配置位置、备份、恢复、外部依赖和费用控制 | 上线方式变化、发布或演练时 |

每个仓库各维护一份项目说明、AI 约定和上线与运维文档；功能单按功能增加。功能单以验收项 AC-01、AC-02 关联检查即可，默认不需要完整 OBJ / US / FR / DES / TASK / RUN 多套编号。

落位建议：

```text
README.md
AGENTS.md                    # 按工具支持方式合并约定，保留原有规则
docs/operations.md
specs/功能名.md               # 一张功能单；不再拆成多份阶段文档
```

文案、样式和小型可逆修正，直接在任务或提交记录写清变化与验证即可。功能单正文以一两页能说明问题为目标，复杂契约和证据通过链接引用。

| 07 测试计划、08 用例、09 报告 | 合并成“验收项—检查—实际结果—证据”一张表 |
| 10 追踪矩阵 | 省去独立文件，用同表的 AC 编号关联 |

| 12 PR 评审 | 省去多人流转和独立评审报告；保留改动前后对照及适当的差异检查 |
| 13 变更申请与缺陷 | 用现有任务或 Issue 记录；需求改变直接更新功能单，Git 保存历史 |
| 14 发布回滚、15 运维复盘 | 合并为一份上线与运维文档；实质故障发生后补一条事实记录 |
| 16 AI 协作约定 | 保留简版，主要通过链接引用项目说明与当前功能单 |
| 17 LLM 评测 | 产品内有大模型时保留小型固定回归样本与结果，可附在功能单中 |
| 18 用户手册 | 自用阶段写必要帮助；邀请外部用户时补一份常见任务与问题说明 |

可以省去的字段与流程：多角色签字、会议纪要、重复的负责人栏、每个阶段的独立审批、手工重复统计、已有工具可生成的清单。

建议持续保留：验收标准、关键权限与数据范围、真实验证结果、数据库迁移、备份恢复、外部服务配置入口与费用控制。AI 每次接手时能找到当前目标、有效规则和未完成工作即可。

## 3. 是否适合“一人公司”的技术架构

文档组织方式和软件部署架构需要分别判断。文档模板本身不要求微服务、容器平台或某种云服务。

针对当前“宝宝计划”，已读取的 package.json 与技术方案显示：使用 Next.js / TypeScript、PostgreSQL，并定义独立 Worker 入口；技术方案采用同一代码库承载 Web、业务逻辑和任务进程。

我的建议是继续保持：

- 一个代码库，按账号、家庭、计划、内容和 AI 等业务职责分模块。
- Web 与后台任务复用业务代码，按运行需要分进程。
- 一个主要关系数据库，保留版本化迁移、必要约束和可验证恢复。
- AI、天气和邮件等外部能力通过少量明确适配入口接入，保留超时、重试和费用限制。
- 从一个确定版本构建、部署、检查与恢复；按实际瓶颈再决定是否拆分。

这是对维护复杂度的判断，不是对服务器容量、可用性或实际部署状态的验证。保留模块边界、先控制分布式运维负担，也与 [Monolith First](https://martinfowler.com/bliki/MonolithFirst.html) 的讨论方向一致；具体建议仍以你的项目条件为依据。

你一个人维护，但产品服务多个家庭，因此家庭隔离、成员权限、并发修改、删除恢复和 AI 写入校验仍应保留关键检查。当前产品内含 AI，可将模型与提示词版本、典型输入、越权反例、失败回退及用量记录放入相应功能单。

## 5. 何时再增加独立文档

出现以下实际需要时再拆出对应文件：

- 接入对外 API 或多个独立调用方：独立维护机器可读接口契约。
- 重大数据迁移、支付或难以回退的操作：独立写清变更、验证与恢复。
- 邀请普通用户试用：补可直接完成任务的用户帮助。
- 引入第二位长期维护者：增加必要的接口说明、贡献规则与审查职责。
- 发生实质故障：补时间线、根因证据、恢复验证和具体改进。

已有“宝宝计划”需求、规格与测试材料先保持原有基线；本精简版用于之后的增量维护，重要旧文档可渐进合并并保留入口。
