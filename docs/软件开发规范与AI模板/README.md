# 软件开发规范与 AI 协作模板包

版本：1.1 · 整理与单人版修订日期：2026-10-31 · 语言：中文 · 格式：Markdown

这套模板将需求、技术设计、实现任务、测试与发布连接起来，适用于个人开发、小型团队和需要交接的产品项目。模板是结合 GitHub 一手资料独立编写的工程整合稿，具体来源及取舍见 [GitHub 参考与选型](00-GitHub参考与选型.md)。

优先建立这条关系：**业务目标 → 需求编号 → 验收条件 → 技术方案 → 开发任务 → 测试与证据 → 发布版本**。

**单人维护入口：** 请优先使用 [单人维护精简版](solo/README.md)，只维护 3 份仓库常驻文档和每个功能 1 张功能单。下方 18 份完整模板作为按需查阅的资料库。

## 1. 从哪里开始

1. 阅读 [完整填写示例](examples/团队任务看板-文档链示例.md)，了解什么程度才算可开发、可验证。
2. 为本次功能创建独立目录，例如 `specs/001-task-completion/`，复制需要的模板。模板目录保存空白母版，功能目录保存实际项目文档。
3. 确认需求及验收条件，再填写方案、任务和测试。尚未确定的事实写入待定项，不能由 AI 默认为已确认。
4. 把文档与代码放进同一个版本库。变更行为时，同步更新需求、契约、测试及说明。
5. 使用 [AI 文档工作流提示词](AI文档工作流提示词.md)推进编写、审查和交接。

**本包中的表格示例、阈值和检查清单均为填写指导，不代表你的项目已执行、已批准或已达标。**

### 个人或小团队的最小组合

单人维护优先采用 [四类精简模板](solo/README.md)：项目说明、AI 协作约定、功能单、上线与运维。需求、必要设计、任务和测试结果集中到功能单；契约与数据结构引用现有权威文件。

需要更细拆分的小团队，可按仓库维护 **05 + 16**；按功能维护 **02 + 简版 03 + 06 + 07/08 + 09**。有部署再加 14，有业务不确定性再加 01，涉及接口或持久化数据时加 04。

微小文案、样式或配置调整可以合并记录为一个 Issue/PR，写清行为变化与适当验证即可。模板服务于风险和协作，不要求每次改动填写全部文件。

### 团队或长期维护项目

采用完整主链 01 → 02 → 03/04 → 06 → 07/08/10 → 09 → 12/14，按影响增加 ADR、变更记录、运维与用户手册。

## 3. 编号与状态

| 对象 | 编号示例 | 用途 |
| --- | --- | --- |
| 业务目标 | OBJ-001 | 对应业务收益与指标 |
| 用户故事 | US-001 | 对应一个用户目标 |
| 功能需求 | FR-001 | 描述一个可验证的系统行为 |
| 非功能需求 | NFR-001 | 描述可测量的质量约束 |
| 验收条件 | AC-001 | 明确通过或失败的判断 |
| 设计项 / 接口 | DES-001 / API-001 | 连接实现方案与契约 |
| 开发任务 | TASK-001 | 连接代码与验证工作 |
| 测试用例 | TC-001 | 连接预期行为与执行结果 |
| 执行记录 / 缺陷 | RUN-001 / BUG-001 | 保存一次执行与故障证据 |
| 变更 / 决策 / 发布 | CR-001 / ADR-001 / REL-001 | 保存影响和历史 |

同一个功能目录内编号唯一；跨功能引用使用“功能目录 + 编号”，例如 `001-task-completion/FR-001`。已有需求不随排序重新编号，删除后保留“取消 / 被替代”的记录。

- 文档：草稿 → 评审中 → 已确认 → 被替代 / 归档。**已确认必须有真实确认人和时间。**
- 开发任务：待开始 → 进行中 → 待验证 → 完成；受阻单独标记原因。
- 测试结果：未执行 / 通过 / 失败 / 受阻 / 不适用。不适用需要理由。
- 验收：未验收 / 通过 / 有条件通过 / 不通过。与测试执行状态分开记录。

## 4. 填写与维护规则

- 占位内容统一用 `{{待填写}}`；无法确认的事实标记 `TBD-001`，同时写明责任人、影响和处理时间。
- 每个“不适用”写一句原因。每个数字阈值写清测量条件、统计口径和确认来源。
- 产品需求说明目标与范围；功能规格保存业务行为；接口契约保存字段和状态码。其他文件通过编号引用，减少重复维护。
- 已发布基线使用 Git tag 或 commit 固定；明确当前有效版本，旧版本不再直接修改。
- 从代码反推文档时，将“观察到的现状”和“已确认的目标”分栏，不能把现有 Bug 自动变成需求。
- 测试证据记录代码版本、配置、环境、命令、退出状态和产物位置。截图只证明截图中可见的行为。
- AI 可以起草和检查；文档确认、测试实际执行和交付验收分别保留真实记录。
- 以上工作流是本模板包的建议，可按项目调整。保留项目已有的强约束和已授权工作方式。

## 5. 建议的项目落位

```text
项目根目录/
├── README.md                   # 项目入口与启动摘要
├── AGENTS.md                   # 按工具支持方式整合 16，保留已有规则
├── docs/
│   ├── product.md              # 01：产品目标与范围
│   ├── development.md          # 05：开发与验证指南
│   ├── adr/                    # 11：重要技术决策
│   ├── runbooks/               # 15：操作与故障处理
│   └── user-guide.md           # 18：用户手册
└── specs/001-feature/
    ├── spec.md                 # 02：行为与验收
    ├── design.md               # 03：技术方案
    ├── contracts/              # 04：API / 数据 / 事件契约
    ├── tasks.md                # 06：任务与执行记录
    ├── test-plan.md            # 07：测试范围与环境
    ├── test-cases.md           # 08：用例
    ├── traceability.md         # 10：需求关联
    ├── verification.md         # 09：实际验证与验收
    ├── release.md              # 14：发布与回滚
    └── evidence/               # 脱敏的日志、报告、截图或证据索引
```

该目录只是一种落位建议，不依赖某个框架、插件或 AI 工具。
