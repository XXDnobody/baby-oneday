2026-10-30 补读了合并函数使用的状态汇总与时间字段，确认本次记录没有另存 `effectiveStatus`、`profileSummary` 或 `statusUpdatedAt` 等覆盖字段；98 条食材档案均有更新时间。将数据库日期还原为日期对象后，在本地运行旧共享函数 `buildEffectiveAllergyRecordsForCloud`，得到 98 项 `passed`；卷心菜、龙利鱼、海带、苦瓜 4 项旧 `untried` 被该函数排除。上述三个样本另用列表函数 `buildAuthoritativeRecordView` 交叉核对，结果一致。控制文档不参与计算。

技术合并关系已澄清，无需用户决定采用哪张表。这是当前工作区源码对只读快照的计算结果，不证明线上部署与该版本相同，也不是对宝宝当前食物反应的重新判断。管理员只需在实际使用前确认旧结论是否仍符合现状。本轮没有调用可能改变状态的旧业务接口，也未读取完整每日排敏过程或进食流水；新系统未采纳或启用这些状态。

### 3.4 偏好与历史的边界

本机偏好键按云环境保存，只有喜欢／一般／避开三个状态。此次模拟器处于“五一”宝宝上下文，但当前家庭键为空，没有确认所选家庭范围，因此没有读取偏好值。常用手机的实际偏好仍需在对应账号和宝宝下核对，或由家庭重新确认近期偏好；不把模拟器或云端空结果写成“无偏好”。

旧计划、每日进食流水、成长记录和全部历史附件未纳入此次内容核查。用户已确认历史计划和流水不进入首批，后置处理；已经查到的食材状态记录不能替代完整历史总量，后续如需复用再确定日期和类别。

## 4. 字段映射建议

以下是结构映射建议；菜谱已进一步形成[逐条审阅清单](首批资料复用清单.md)，实际导入清单与新实体标识尚未生成。新系统实体仍是[接口与数据模型](接口与数据模型.md)中的设计草案。

| 旧数据 | 新系统位置 | 转换原则 |
| --- | --- | --- |
| 宝宝 `nickname/name` | `children.nickname` | 使用家庭确认的显示称呼，避免不必要地复制真实姓名 |
| `birthDate` | `children.birth_date`，或确认后的月龄依据 | 只有确认真实值时才保留；不从演示的 17 个月倒推生日；不把旧月龄策略直接当新系统规则 |
| 旧账号、家庭、宝宝标识 | 独立迁移映射到新 `user/household/child` 标识 | 保留来源关系用于去重与核查；微信身份不直接充当新系统邮箱账号，不自动创建成员或邀请 |
| 排敏资料、禁用规则 | `food_profiles` 的待确认输入 | 分清“尝试过”“历史反馈”“当前禁忌”与普通偏好，保留日期及依据，管理员确认后才影响新计划 |
| 本机食材喜欢／避开 | `preferences` | 获取实际值后确认当前是否仍有效并设置适用期限；“避开”不自动变过敏；缺失保持未知 |
| 个人或系统菜谱 | `content_items` / `content_versions` | 保留标题、原料、步骤、说明、来源标识和版本；个人内容留在本家庭，系统内容单独核查 |
| 用量映射 | 内容版本中的原料用量及依据 | 不丢失单位、份数及不确定状态；不使用 AI 补造缺失数值作为事实 |
| 来源台账、旧审核与改编记录 | `content_sources` / `content_source_links` 及核对状态 | 来源事实、内部标准化、家庭认可、专业审核分别标注，保留后续降级或阻断结论 |
| 旧启用标记 | `household_content_settings` 的候选输入 | 仅你作为新家庭管理员决定启用范围，旧值不直接开通全部内容 |
| 旧计划、实际反馈和进食记录 | 视后续选择映射为计划或历史记录 | 计划不等于实际发生，单次反应不自动生成长期偏好；不在本轮默认搬全部历史 |
| 家庭照片、头像、记录图片 | 不进入当前迁移范围 | 本产品已取消家庭照片功能；本轮未删除旧图或原始文件 |
